# Project Agent Notes

WedPlan client: a single-page wedding-planning marketing site. No backend, test suite, CI workflows, or README in this repo.

## Commands

- `npm run dev` — dev server. If one is already running, `next dev` reports the existing URL/PID instead of starting a second one.
- `npm run lint` — ESLint 9 flat config (`eslint.config.mjs`), no file args.
- `npx tsc --noEmit` — typecheck; there is no `typecheck` script.
- `npm run build` / `npm run start` — production build and serve.
- Verify changes with lint + `tsc` + loading `/`; there is nothing else to run.

## Next.js 16 Specifics

- Read the version-matched docs in `node_modules/next/dist/docs/` before using App Router APIs.
- The marked Next.js agent rules block above is generated by `next dev`. Never remove or modify it.
- `next.config.ts` enables `cacheComponents` and `partialPrefetching` (PPR is the default).
- Do not add `export const dynamic`, `revalidate`, or `fetchCache` exports to route files, and do not add a `runtime` export — these error or are unsupported with Cache Components.
- Cache with `"use cache"` + `cacheLife`, or wrap request-time data in `<Suspense>`.
- For prerender build failures, use `next build --debug-prerender` to get source-mapped stacks and check all routes instead of stopping at the first.
- Never assume APIs from older Next.js versions are compatible with the installed version.

## UI Conventions

- Tailwind CSS 3.4, not v4: keep the `@tailwind base/components/utilities` directives in `src/app/globals.css` and configure styles in `tailwind.config.ts`.
- Brand tokens live in `tailwind.config.ts`:
  - `wedplan-ink`: `#2d2725`
  - `wedplan-cream`: `#fffaf7`
  - `wedplan-rose`: `#96575b`
- Add new brand colors to `tailwind.config.ts`, not directly to `globals.css`.
- HeroUI 2 is wired through `src/app/providers.tsx` (`HeroUIProvider`, a client component) in the root layout.
- Add new global providers through `src/app/providers.tsx`.
- HeroUI's theme is not customized; brand color is applied per component with `className` (e.g. `bg-wedplan-rose`).
- A bare HeroUI component uses its default palette.
- `src/app/page.tsx` is the only page and is a single client component with inline data arrays; there is no `src/components` directory yet.
- Follow existing design patterns instead of introducing a completely different visual style.

## Code Review and GitHub Push Workflow

When I ask you to review my current changes and push them to GitHub, follow this complete workflow.

### Step 1: Inspect Git Changes

- Check `git status`.
- Identify the current branch and configured remote.
- Inspect all modified, added, and deleted files.
- Review the complete Git diff.
- Identify the intended changes.
- Distinguish my current task changes from pre-existing uncommitted work.
- Never assume all uncommitted changes belong to the current task.

### Step 2: Perform Code Review

Carefully review all intended changes for:

- Logical errors and incorrect behavior.
- Potential bugs and regressions.
- Security vulnerabilities.
- Incorrect React or Next.js usage.
- Deprecated or incompatible APIs.
- TypeScript errors.
- Responsive design problems.
- Accessibility issues.
- Performance problems.
- Unnecessary code or duplicated logic.
- Violations of existing project conventions.

Report significant findings with file names and clear explanations.

Do not report speculative issues as confirmed bugs.

### Step 3: Resolve Issues

- If significant issues are found, explain them before proceeding.
- Do not silently ignore or hide review findings.
- Do not automatically make unrelated changes.
- Fix identified issues only when the required behavior is clear.
- Ask me when a fix requires a product or design decision.
- Re-review the affected code after fixing issues.
- Do not commit or push while significant unresolved issues remain.

### Step 4: Run Verification

Run the following commands when appropriate:

1. `npm run lint`
2. `npx tsc --noEmit`
3. `npm run build`

Also verify relevant application pages when possible.

- Check the actual output of every command.
- Investigate failures instead of ignoring them.
- Distinguish pre-existing failures from failures introduced by current changes.
- Never claim successful verification without evidence.
- Do not proceed to commit if relevant verification failures remain unresolved.

### Step 5: Prepare the Commit

After successful review and verification:

- Confirm that no sensitive or unrelated files are included.
- Stage only the intended changes.
- Prepare a meaningful Conventional Commit message.
- Show me the changed files.
- Show me the proposed commit message.
- Provide a concise code review and verification summary.

### Step 6: Request My Approval

Before creating the commit or pushing to GitHub, ask for my explicit approval.

Do not commit or push until I approve.

Approval to review or test does not mean approval to commit or push.

### Step 7: Commit and Push

After receiving my approval:

- Create the commit using the approved message.
- Push to the configured GitHub remote and current branch.
- Never force push.
- Never overwrite remote history.
- If the remote branch has unexpected changes or a conflict occurs, stop and explain the situation.
- Never resolve conflicts by discarding my work without permission.

### Step 8: Final Report

After completing the workflow, report:

- Summary of reviewed changes.
- Issues identified and resolved.
- Lint results.
- TypeScript results.
- Build results.
- Files included in the commit.
- Commit message.
- Commit hash.
- GitHub push status.

If the push fails, clearly report that it was not successful.
